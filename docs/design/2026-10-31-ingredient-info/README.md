# 재료 정보 질문 설계안 (2026-10-31, 구현 전)

상태: **1차 구현(2026-11-01, 미커밋, 기능 꺼짐)**. 근거 실험은 `poc/ingredient-rag/`(추적 안 함)에 있습니다. 구현하면서 바뀐 점은 §12에 적었습니다.

## 1. 문제
- "무청이 뭐야?"는 `ChatIntentClassifier`에서 `GENERAL_CHAT`이 되고, "시래기랑 우거지 차이"는 `차이` 때문에 `COOKING_QUESTION`이 됩니다. 둘 다 `ChatService.processChat`의 일반 대화 경로로 가서 `OllamaLlmService.getChatResponse`가 근거 없이 답합니다(`ChatService.java:388`).
- 실험 결과(qwen3:8b, 서비스와 같은 지시문·설정): 재료 질문 50개 중 약 3개만 맞혔고, 자료에 없는 재료는 5개 모두 지어냈습니다(무우청="무를 청량음료처럼 마시는 방식", 냉이="Lettuce" 등).
- 같은 모델에 자료를 주면 정답률이 크게 오릅니다(PoC v1: 49/50, v2 결과는 §8).

## 2. 목표와 범위
- 목표: 재료가 **무엇인지**(정체·분류·다른 이름·두 재료의 차이·무엇으로 만드는지)를 묻는 질문에 **검토된 자료로만** 답하고 출처를 보여 줍니다. 자료가 없으면 지어내지 않고 "확실하지 않아요"라고 답합니다.
- 범위 밖(지금 경로 유지):
  - 레시피·조리법 요청, 직전 레시피 후속 질문.
  - 효능·영양·질병 관련 질문("당뇨에 좋아?"): 의료 조언처럼 보일 수 있어 이 기능으로 답하지 않습니다.
  - **먹어도 되는지**를 묻는 질문("땅콩 먹어도 돼?"): 안전 판단은 하지 않습니다. 기존 알레르기 정책을 그대로 따릅니다.

## 3. 전체 흐름
```
사용자 메시지
 └ ChatService.processChat
    ├ (기존) 재작성·의도 분류·승인 레시피·레시피 후속 처리
    ├ (기존) 로그인 사용자의 건강 정보를 못 읽으면 중단
    ├ (신규) IngredientInfoService.answer(message, safetyContext)   ← 레시피 요청·상세 후속·레시피 질문이 아닐 때만
    │    1. 질문 형태 확인: "X(이)가 뭐야 / X는 무슨 과·어떤 채소 / X 다른 이름·정식 이름 / X랑 Y 차이 / X는 뭘로 만들어"
    │    2. 재료 이름 찾기(이름 우선 검색) → 자료 선택
    │    3. 근거 채택 → 원문 문장 추출(LLM 없음). 채택된 문서가 없으면 보류
    │    4. 알레르기 주의 문구(기존 appendAllergyCautionIfMentioned)
    │    → Optional.empty()면 기존 일반 대화로 그대로 진행
    └ (기존) 일반 대화 LLM
```

## 4. 자료(코퍼스)
- 파일: `backend/src/main/resources/ingredients/ko-ingredients.json` (ko-allergens.yaml처럼 저장소에 넣고 리뷰를 거쳐 바꿈).
- 만드는 방법: `backend/tools/ingredients/build_corpus.py`가 위키백과 API(`action=query`, `exintro`, 최대 4문장)로 받아 **사람이 검토한 뒤** 커밋합니다. 서버는 실행 중에 위키백과를 부르지 않습니다.
- 항목: `id, title, text, url, related_terms[], image{file, author, license, licenseUrl, filePageUrl} | null, reviewedAt, source:"ko.wikipedia", revisionId`.
- 받을 때 자동으로 뺌: 동음이의 문서, 문서 없음, 음식·생물 설명이 아닌 문서. **사람이 뺌**: 잘못된 넘겨주기 목록(`excluded.json`).
  - PoC에서 실제로 걸린 예: 근대→역사 시대, 황태·조기·민어→동음이의 문서, 꼬시래기(해조류)→풀망둑(물고기).
- 넘겨주기(redirect)는 **같은 말이 아니라 관련 검색어**로만 저장합니다. 예: 코다리→명태(실제로는 반쯤 말린 명태), 깻잎→들깨(잎과 식물).
- 라이선스: 위키백과 글은 CC BY-SA 4.0입니다. 답변에 **문서 링크, "위키백과", 라이선스**를 표시합니다. 답변이 원문을 거의 그대로 옮기므로 이 표시는 필수입니다.
- 첫 배포 규모: PoC v2의 256개(제외 23개)부터 시작하고, 검토를 거쳐 늘립니다.

## 5. 검색과 근거 채택 (두 단계로 나눔)
PoC v2에서 **유사도 기준점만으로는 자료 유무를 가를 수 없음**을 확인했습니다. 임베딩 점수가 재료 이름보다 질문 형태("~는 뭐야?")에 더 크게 반응했습니다(§8). 그래서 **후보 찾기**와 **답의 근거로 채택**을 나눕니다(Codex 설계 검토 1회차 P2-1).

### 5.1 후보 찾기
1. 질문 낱말에서 조사를 뗍니다. 아는 이름(제목·관련 검색어)이 되는 후보를 먼저 고릅니다. "매생이는"은 "매생"이 아니라 "매생이"로, "고추냉이랑"은 "고추냉"이 아니라 "고추냉이"로 봅니다.
2. **정확한 이름**: 제목(괄호 앞)과 같으면 그 문서. "송이버섯"·"명이나물"처럼 뒤에 버섯·나물이 붙어도 맞춥니다. 두 재료를 물으면 두 문서를 모두 가져옵니다.
3. **관련 검색어**: 검토된 넘겨주기 목록(related_terms)과 같은 경우, 또는 제목이 "이름+나무/버섯/나물/류"인 경우(두릅→두릅나무).
4. **본문 언급**: 그 낱말이 본문에 나오는 문서. 최대 2개이며, 임베딩 점수로 순서를 정합니다.
5. **임베딩만**: 1~4가 모두 없을 때 bge-m3 점수가 0.58 이상인 문서 1개.

### 5.2 근거로 채택 (이 조건을 통과한 문서만 답에 씁니다)
| 후보 종류 | 채택 조건 | 답 |
|---|---|---|
| 정확한 이름 | 항상 | 원문 추출 |
| 관련 검색어 | 본문에 그 이름을 **직접 부르는 문장**이 있으면 그 문장을 근거로 씀 | 원문 추출 |
| 관련 검색어 | 그런 문장이 없음 | 정해진 문장: "‘곤드레’는 위키백과에서 ‘고려엉겅퀴’ 문서로 연결돼요. 같은 것인지는 자료에 적혀 있지 않아요." + 원문 추출 |
| 본문 언급 | 본문에 그 이름을 직접 부르는 문장이 있을 때만 | 원문 추출 |
| 본문 언급 | 이름이 나오기만 함 (예: "민어"가 참조기 본문의 "민어과"에 걸림) | **채택하지 않음** |
| 임베딩만 | 항상 채택하지 않음. 1차에서는 "혹시 ~를 찾으셨나요?" 제안도 하지 않음 | — |

- "직접 부르는 문장"의 예: "광어(廣魚)라고도 하는데", "흔히 조기라고 불리며", "어린 개체는 노가리라 부른다", "새송이로도 알려져 있는", "정향이라는 이름이 붙었다".
- 채택된 문서가 하나도 없으면 보류합니다: "확실하지 않아요. 검토된 자료에서 찾지 못했어요."
- **질문 대상별로 채택 여부를 따로 기록합니다**(Codex 검토 3회차). 비교 질문은 "X(이)랑/와/과/하고 Y" 형태에서 대상 X·Y를 뽑습니다.
  - 모두 채택되면 재료별 원문을 보여 줍니다.
  - 일부만 채택되면 채택된 재료의 원문을 보여 주고, 채택되지 않은 재료마다 "‘민어’는 검토된 자료에서 찾지 못했어요."를 **같은 답 안에 따로** 적습니다. 두 재료가 어떻게 다른지는 말하지 않습니다.
  - 모두 채택되지 않으면 전체를 보류합니다.
  - 임베딩 장애 중에도 같은 규칙입니다(채택 판단이 문자열 기준이기 때문).
- 임베딩 계산: Ollama `/api/embed`, 모델 `bge-m3`(1.2GB). 서버가 시작할 때 자료 문서와 문장 벡터를 계산해 메모리에 둡니다(256개 문서, 문장 약 900개). 벡터 DB는 쓰지 않습니다.
- **임베딩 실패 시**: 5.1의 2~4(문자열 일치)만 씁니다. 임베딩 실패가 영향을 주는 곳은 아래 두 가지뿐입니다.
  - 5.1의 5(임베딩만) 단계를 끕니다.
  - §6의 "질문과 가장 비슷한 추가 문장"을 생략합니다(본문 언급 후보가 여럿이면 순서는 자료 파일 순서로 정함).
  - 근거 채택(5.2)과 그 근거 문장 출력은 문자열로만 판단하므로 바뀌지 않습니다. 이름을 직접 부르는 문장(예: "어린 개체는 노가리라 부른다")과 관련 검색어 안내 문장은 장애 중에도 반드시 나옵니다. 이 근거를 확보하지 못하면 보류합니다.
  - 실패를 "자료 없음"으로 바꾸지 않고, 채택된 문서가 없으면 보류합니다.

## 6. 답 만들기: LLM 없이 원문 추출
Codex 검토 1회차 P2-2를 반영했습니다. 낱말 포함률 검사로는 LLM이 두 재료의 설명을 맞바꾸거나 관계를 뒤집은 답을 잡지 못합니다. 그래서 **1차에서는 이 경로에서 LLM을 부르지 않습니다.**
- 채택된 문서마다 **첫 문장(정의) + 나머지 문장 중 질문과 임베딩이 가장 비슷한 문장 1개**를 원문 그대로 보여 줍니다. 근거 채택이 "이름을 직접 부르는 문장"으로 된 경우에는 그 문장 + 첫 문장을 씁니다.
- 두 재료 차이 질문은 **재료마다 따로** 원문 문장을 보여 줍니다. 무엇이 다른지 요약하는 문장은 만들지 않습니다. 섞거나 바꿔 말할 수 없게 하기 위해서입니다.
- 장점: 지어낸 문장이 0개이고 바로 답합니다(LLM 호출이 없어 수십 ms). 단점: 문장이 사전처럼 딱딱하고, 질문에 딱 맞는 문장을 못 고를 때가 있습니다(§8 오답 유형).
- 나중에 LLM 요약을 다시 넣는다면, 재료와 문장의 대응을 강제하는 형식(예: 재료별 칸에 인용 번호만 고르게 함)과 설명 교환·관계 반전 테스트를 먼저 만듭니다. 1차 범위가 아닙니다.
- 알레르기: 답이 나온 뒤 기존 `appendAllergyCautionIfMentioned`를 그대로 붙입니다. 질문과 답에 등록 알레르기와 관련된 재료가 있으면 주의 문구가 붙습니다. 이 기능은 "안전하다"는 말을 하지 않습니다. 질문 형태 조건에서 "먹어도 돼/괜찮아/알레르기"가 들어간 질문은 처음부터 제외합니다.

## 7. 응답·화면
- `ChatDto.Response`에 선택 필드 `ingredientInfo`를 추가합니다. 값이 없으면 null이라 기존 클라이언트에 영향이 없습니다.
  ```json
  "ingredientInfo": {
    "items": [{"title": "무청", "url": "https://ko.wikipedia.org/wiki/무청", "basis": "name|related_named|related|text_named",
               "image": {"url": "/api/ingredients/images/{id}", "author": "...", "license": "CC BY-SA 3.0", "filePageUrl": "..."} }],
    "sourceLabel": "위키백과 (CC BY-SA 4.0)"
  }
  ```
- **출처는 답변 본문에도 넣습니다**(Codex 1회차 P2-3). 본문 끝에 다음 한 줄을 붙여 저장합니다: `출처: 위키백과 「무청」 일부 발췌 https://ko.wikipedia.org/wiki/무청 (CC BY-SA 4.0)`. 대화 기록 복원(`ChatHistoryMessageDTO`)은 본문만 돌려주므로, 새 대화와 복원한 대화 모두에서 링크와 라이선스가 남습니다. 복원할 때 사라지는 것은 사진과 카드 모양뿐입니다. 이를 복원하려면 V30 마이그레이션이 필요하므로 **1차에서는 하지 않습니다**.
- 사진:
  - 확정 디자인(`2026-10-30-salus-final-direction`)이 음식 사진을 장식으로 쓰지 않으므로, 사진은 **기본으로 접어 두고 "사진 보기"를 눌렀을 때만** 보여 줍니다. 장식이 아니라 재료를 알아보기 위한 정보입니다.
  - 자료를 만들 때 썸네일을 받아 두고 **우리 서버에서** 제공합니다. 사용자 브라우저가 위키미디어에 직접 접속하지 않게 하기 위해서입니다. 처리방침을 바꿔야 하는지는 따로 확인합니다(§11).
  - 작가·라이선스·원본 링크를 사진 아래에 표시합니다. 라이선스 정보가 없는 사진은 쓰지 않습니다.
- 화면: `ChatScreen`의 말풍선 아래에 작은 출처 카드(제목·링크·"사진 보기")를 둡니다. 레시피 카드와 다른 모양이고, "내 레시피에 저장" 같은 버튼은 없습니다.

## 10. 테스트 계획
- `IngredientInfoServiceTest`(단위):

  - 차이 질문: 재료마다 자기 문서의 문장만 나옴. A의 문장이 B 칸에 들어가지 않음.

  - 임베딩 실패: 문자열 일치로만 답하고, 없으면 보류. 예외가 "자료 없음"으로 바뀌지 않음. 임베딩이 실패해도 노가리→명태 답에 "어린 개체는 노가리라 부른다" 문장이 남고, 코다리→명태 답에 "같은 것인지는 자료에 적혀 있지 않아요" 문장이 남음.
  - 보류 시 LLM이 불리지 않음. 이 경로 전체에서 LLM이 불리지 않음.

## 11. 남은 위험
- **처리방침·라이선스**: 서버는 실행 중에 사용자 질문을 위키백과나 위키미디어로 보내지 않습니다. 사진도 우리 서버에서 제공하므로 새 제3자 제공은 없다고 판단합니다. 법적 검토는 아닙니다. CC BY-SA 표시(출처·라이선스·변경 여부)는 답변 본문과 사진 아래에 넣습니다. 원문을 문장 단위로 잘라 쓰는 것은 '변경'으로 볼 수 있으므로 "일부 발췌"라고 표시합니다.
- **이름 일치의 한계**: 오타("무우청")나 처음 보는 표현은 임베딩 3단계에 맡기는데, 기준점이 높아 보류될 수 있습니다. 틀린 답보다 보류가 낫다고 보고 받아들입니다.
- **동음이의 오탐**: 질문이 재료 이야기가 아닐 때(예: "김이 뭐야?"가 사람 성씨) 재료 답이 나올 수 있습니다. 질문 형태 조건과 STOP 낱말로 줄이지만 완전히 막지는 못합니다.
- **위키백과 내용 자체의 오류**: 예를 들어 근대 문서가 "근대 또는 비트"라고 적어 두 채소를 섞고, 고추냉이 문서에 편집자 메모가 섞여 있습니다. 사람 검토로 걸러야 하며, 검토 기록(`reviewedAt`)을 남깁니다.
- **평가 세트를 만든 사람이 같음**: 질문과 정답을 같은 사람이 만들었습니다. PoC 도중 생긴 일반적인 버그(조사 처리, 긴 이름이 짧은 이름을 가리는 문제)는 test 세트를 본 뒤 고쳤습니다. 배포 전에 다른 사람이 만든 질문으로 한 번 더 잽니다.

## 12. 구현하면서 바뀐 점 (2026-11-01)
- **질문 판별은 문장 구조로**: PoC의 STOP 낱말 목록 대신 "[재료][조사] [정체를 묻는 서술어]" 모양만 받습니다(`IngredientQuestionParser`). 서술어는 한국어 의문사(뭐·무엇·무슨·어떤·어느·어디)와 이름·원료를 묻는 말로 시작해야 합니다. 손질·보관·효능·"먹어도 돼" 질문은 모양이 달라 받지 않습니다.
- **재료 이름 사전은 자료 그 자체**: 문서 제목, 넘겨주기 이름, 검토된 자료가 없는 이름(`unreviewedNames`: 민어·황태 등 동음이의 문서)을 씁니다. 코드에 재료 이름을 두지 않습니다.
- **임베딩만으로 찾는 단계와 기준점(0.58)을 없앴습니다**: 그 단계는 어차피 근거로 채택하지 않으므로 기준점이 필요 없습니다. 임베딩은 '질문과 가장 비슷한 추가 문장'과 본문 언급 문서 순서에만 씁니다.
- **이름을 묻는 질문**("다른 이름은?")은 이름을 적은 문장(라고도·라 부른다·이름·표준어)을 먼저 고릅니다. 임베딩은 "양배추 머리는 0.5~4kg" 문장을 골랐습니다(dev 1문항).
- **자료가 모르는 이름**(퀴노아·김치찌개)도 질문 모양이 맞으면 일반 대화로 넘기지 않고 보류합니다(§13). 1차 설계(일반 대화로 넘김)에서 바꿨습니다.
- 자료 파일: `backend/src/main/resources/ingredients/ko-ingredients.json`(문서 251, 검토된 자료 없음 28).
- **자료 검토 장치**(Codex 구현 검토 2회차 P2): 사람이 읽고 뺀 문서는 `excluded_documents.tsv`(고추냉이: 와사비 동일시와 편집자 메모가 모순, 근대: "근대 또는 비트", 오징어: "오징어 또는 낙지", 닭고기: 장난성 편집, 고춧가루: 근거 불분명한 주장). 장난성 편집·편집자 메모 흔적(ㅋ, !!, ??, 근데, 자모만)이 있는 문서는 자동으로 빼고, 사람이 읽고 확인하면 `approved_documents.tsv`에 올립니다. 빠진 문서의 이름과 넘겨주기 이름은 보류 대상(unreviewedNames)이 됩니다. 테스트가 남은 문서에 이런 흔적이 없는지 확인합니다. 만드는 도구: `backend/tools/ingredients/build_corpus.py`, 이름 목록 `names.txt`, 잘못된 넘겨주기 `bad_redirects.tsv`. 발음 기호·한자·학명만 든 괄호는 뺍니다. **켜기 전에 사람이 자료를 읽고 확인해야 합니다**(예: 근대 문서의 "근대 또는 비트", 고추냉이 문서의 편집자 메모).
- 사진은 1차에서 넣지 않았습니다. 썸네일 약 245장과 사진별 라이선스를 받아 저장소에 넣어야 해서 따로 진행합니다. 출처 링크는 화면 카드(누르면 원문)와 답변 본문 양쪽에 있습니다.
- 일반 대화 지시문도 나눴습니다: `LlmService.Task`로 호출 목적(일반 대화·검색 근거 레시피·상세 설명·재료 추천 레시피·식단 요약)을 호출하는 쪽이 정하고, 메시지 안의 표식으로 추측하지 않습니다. 일반 대화 지시문에서 레시피 출력 형식을 뺐습니다(일반 대화에서 나온 레시피는 안내 문구로 바뀌어 사용자가 답을 못 받음).
