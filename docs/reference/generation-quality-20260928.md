# 레시피 생성 통과율 개선 기록 (2026-09-26 ~ 09-28)

`qwen3:8b` 단독 4/12(33%)에서 9/12(75%)까지 올린 과정과 근거입니다. 모든 수치는 같은 하네스(`eval.sh`), 같은 12케이스, 같은 모델로 측정했습니다.

## 결과

| 단계 | 통과 | 점수 |
|---|---:|---:|
| 시작 | 4/12 (33%) | 76.7 |
| + 모델 폴백 | 7/12 (58%) | 88.8 |
| + 대체 방향 `const` | 8/12 (67%) | 86.7 |
| + 오븐 온도 `contains` | 9/12 (75%) | 89.2 |

### 이 표를 읽을 때의 경고

**각 행은 1회 측정입니다.** 같은 코드 상태에서 실행을 반복하면 결과가 달라집니다.

| 실행 | 통과 |
|---|---|
| eval-fb5 | 9/12 |
| eval-fb7 | 9/12 |
| eval-final | 7/12 |

세 실행 모두 코드가 같았습니다. 실행 안에서 생성은 결정적이지만(24개 조합 전부 3/3 또는 0/3) 실행 사이에는 모델 재로드로 결과가 달라집니다.

따라서 위 표의 단계별 증가분은 **경향이지 확정된 효과가 아닙니다.** 4/12에서 9/12로의 전체 이동은 폭이 커서 신뢰할 만하지만, 개별 단계의 +1은 변동 범위 안에 있습니다. 확정하려면 각 설정을 별도 실행으로 3회 이상 반복해야 합니다.

지연은 실행마다 63~152초로 흔들려 비교에 쓰지 않습니다.

## 무엇이 통했고 무엇이 통하지 않았는가

### 통하지 않음 — 프롬프트에 규칙 추가

생성 프롬프트에 규칙이 27개 있습니다. 여기에 한 줄을 더하면 다른 규칙이 밀려납니다.

| 변경 | 통과 |
|---|---|
| 프롬프트 수정 3건 | 8/24 |
| + 시간 일관성 규칙 한 줄 | 7/24 |
| 그 한 줄 제거 | 10/24 |

시간 규칙을 넣자 `TIME_CONFLICT`는 줄었지만 `PROTEIN_DONENESS_CUE_REQUIRED`가 재발하고 `COOKING_HEAT_REQUIRED`가 늘었습니다. 되돌리자 회복됐습니다.

### 통함 — 다른 모델로 폴백

`repeat 3` 측정에서 24개 (모델, 케이스) 조합이 전부 3/3 아니면 0/3으로 갈렸습니다. 실행 안에서는 생성이 결정적이므로 같은 모델로 repair하면 같은 실패가 반복됩니다.

두 모델의 실패 지점은 거의 겹치지 않습니다.

| 모델 | 통과 |
|---|---|
| qwen3:8b 단독 | 7/12 |
| gemma3:4b 단독 | 5/12 |
| 둘 중 하나라도 | 10/12 |

공통 실패는 2건뿐이고 그중 1건은 오탐입니다. `RecipeGenerationCoordinator.fallbackModelOrFail`이 repair 실패 후 다른 모델로 새로 생성합니다. repair 프롬프트가 아니라 생성 프롬프트를 씁니다. 실패한 초안을 고치는 것이 아니라 다른 모델의 강점으로 처음부터 만드는 것이 목적입니다.

### 통함 — 스키마로 강제

프롬프트로 부탁하는 대신 JSON Schema로 구조를 고정합니다. 모델이 규칙을 기억할 필요가 없어집니다.

**단계별로 배운 것:**

| 방법 | 결과 |
|---|---|
| `required`만 추가 | 부족. 키는 넣고 값에 `null`을 채움 |
| 타입에서 `null` 제거 | 실제 값이 들어옴 |
| `const`로 값 고정 | 의미까지 고정됨 |
| `contains` + `minContains` | 배열 안에 특정 조건 항목을 강제 |

`required`가 "키 존재"만 보장하고 `null`을 막지 않는다는 점이 결정적이었습니다.

**적용 사례 1 — 대체 요청의 `adjustments`**

`minItems: 1`만 걸었을 때 모델이 배열을 채우긴 했으나 내용이 틀렸습니다.

```json
{"fromIngredient": "두부", "toIngredient": "돼지고기", "quantityAdjustment": null}
```

요청은 돼지고기 → 두부였는데 방향이 뒤집혔습니다. 검증기는 요청의 `from`과 일치하는 항목을 찾으므로 `ADJUSTMENT_REASON_MISSING`과 `QUANTITY_ADJUSTMENT_MISSING`이 동시에 납니다.

대체가 한 건일 때 `const`로 방향을 고정하고 `quantityAdjustment`의 타입에서 `null`을 뺐습니다. 대체가 여러 건이면 항목별 고정이 불가능해 적용하지 않습니다.

**적용 사례 2 — 오븐 온도**

모델이 온도를 알고 있는데 필드를 비웠습니다.

```
instruction: "에어프라이어를 190도에서 20분간 구워줍니다"
temperatureC: null
```

프롬프트로 세 번 안내해도 고쳐지지 않았습니다. 어느 단계가 가열인지는 생성 결과에 달려 있어 특정 단계에 값을 박을 수 없으므로, `contains`로 "온도를 가진 단계가 최소 하나"를 요구했습니다. 요청 문구에 오븐·에어프라이어가 있을 때만 겁니다. 팬 조리는 `temperatureC`가 `null`이어야 합니다.

### 통함 — 검증기 오탐 제거

`RecipeDraftValidator`가 `instruction`에 "에어프라이어"가 있으면 무조건 가열 단계로 보고 온도와 시간을 요구했습니다. "에어프라이어에서 감자를 꺼내어 식힙니다" 같은 단계까지 실패시켰습니다.

기구 언급과 실제 가열 동작을 분리했습니다.

```java
boolean ovenStep = applianceMentioned && !nonHeatingHandling;
```

가열 동사가 하나라도 있으면 취급 표현이 있어도 가열 단계로 봅니다. 판정을 느슨하게 한 곳은 온도·시간 요구뿐이고, `NON_OVEN_TEMPERATURE_FORBIDDEN`은 기존 기준을 유지했습니다. targeted test 4건으로 우회 가능성을 막았습니다.

## 측정 방법론에서 배운 것

1. **절전 차단이 없으면 결과가 무효가 됩니다.** 1차 실행은 시스템이 74회 sleep/wake해 29시간을 쓰고 리포트를 남기지 못했습니다. 벽시계 기반 측정이 수면 구간을 포함했고 Reactor 타임아웃도 함께 멈춰 상한이 동작하지 않았습니다. `caffeinate -dimsu`로 감싸야 합니다.

2. **`repeat`로는 변동성을 못 잽니다.** 실행 안에서 생성은 결정적입니다(24개 조합 전부 3/3 또는 0/3). 변동성을 보려면 같은 설정으로 실행 자체를 반복해야 합니다.

3. **모델 언로드 없이 순차 실행하면 3번째 모델부터 지연이 오염됩니다.** 평가 중 2.3 tok/s였던 `gemma2:9b`가 단독 실행에서는 15.3 tok/s였습니다. RAM 16GB에서 5GB급 모델이 겹쳐 상주하기 때문입니다.

4. **타임아웃을 무제한으로 두면 안 됩니다.** 안전밸브가 사라져 느린 모델이 실행을 붙잡습니다. 측정용으로 넉넉히 두되 반드시 상한을 둡니다.

### 출력 길이를 조이는 것도 역효과

토큰 예산을 늘리지 못하니 반대로 출력을 줄여 보았습니다. 단계 필드 상한을 낮췄습니다.

| 필드 | 원래 | 시도 |
|---|---:|---:|
| instruction | 180자 | 100자 |
| completionCue | 120자 | 70자 |
| recoveryTip | 120자 | 80자 |

결과는 9/12에서 6/12로 하락했습니다. `TIME_CONFLICT`가 3건으로 최상위 실패가 됐고 `COMPLETION_CUE_REQUIRED`와 `PROTEIN_DONENESS_CUE_REQUIRED`가 재발했습니다.

완료 기준을 짧게 쓰게 만든 것이 원인으로 보입니다. "중심까지 완전히 익어 핏물이 없는 상태" 같은 표현은 70자 안에 담기 어렵고, 검증기는 그 표현을 요구합니다. `OUTPUT_TOKEN_LIMIT` 1건을 없애려다 3건을 새로 만들었습니다. 원래 값으로 되돌렸습니다.

**토큰 예산 문제는 양방향 모두 막혀 있습니다.** 늘리면 알레르겐이 섞이고 줄이면 검증 품질이 떨어집니다. 남은 방향은 프롬프트 자체를 압축해 입력 토큰을 줄이거나(현재 1,100~1,450 토큰), 스키마에서 선택 필드를 덜어내는 것입니다.

## 남은 실패

| 케이스 | 코드 | 성격 |
|---|---|---|
| `chat-allergy-shrimp-question` | `ALLERGEN_CONFLICT(새우)` | 오탐. 모델은 새우 없는 요리를 정확히 추천 |
| `recipe-allergy-wheat-gamjajeon` | `OUTPUT_TOKEN_LIMIT` | 스키마 제약으로 출력이 길어져 900 토큰 한도 초과 |
| `recipe-exclude-pork-kimchi-jjigae` | `DECLARED_INGREDIENT_NOT_USED`, `PROTEIN_DONENESS_CUE_REQUIRED` | 미해결 |

`OUTPUT_TOKEN_LIMIT`은 스키마 강제의 부작용입니다. 상위 응답들이 900, 878, 777, 764로 한도에 몰려 있습니다.

### 토큰 한도를 올리면 안 되는 이유

`num_predict`를 900에서 1300으로 올려 측정했습니다. `OUTPUT_TOKEN_LIMIT`은 사라졌지만 통과율이 9/12에서 8/12로 떨어졌고, **우유 알레르기 사용자에게 우유가 든 레시피가 나왔습니다.**

```
재료:      감자, 양파, 육수, 우유
safetyNotes: ["알레르기: 우유"]
```

모델이 알레르기를 인지하고 `safetyNotes`에 적어 놓고도 재료에 넣었습니다. `RecipeDraftValidator`와 `AllergenMatcher`가 `HARD_FAIL`로 잡아 사용자에게 나가지는 않았습니다.

**처음에는 토큰 확대가 원인이라고 판단했으나 틀렸습니다.** 이후 기본값 900으로 되돌린 실행에서 같은 케이스에 같은 누출이 재현됐습니다.

```
재료:        감자, 양파, 육수, 우유
safetyNotes: ["알레르기: 우유"]
```

토큰 예산과 무관하게 `qwen3:8b`가 이 케이스에서 주기적으로 우유를 넣습니다. 기본값 900은 유지하되, 그 근거는 알레르겐이 아니라 통과율입니다.

이 세션에서 관측된 실제 알레르겐 누출은 세 번입니다.

| 회차 | 모델 | 조건 |
|---|---|---|
| 1 | gemma3:4b | 기본 설정 |
| 2 | qwen3:8b | num_predict 1300 |
| 3 | qwen3:8b | num_predict 900 |

세 번 모두 모델이 `safetyNotes`에 알레르기를 적어 놓고도 재료에 넣었고, 세 번 모두 `RecipeDraftValidator`와 `AllergenMatcher`가 차단해 사용자에게 나가지 않았습니다.

**이것이 이 세션에서 가장 중요한 관측입니다.** 모델은 알레르기를 인지한 상태에서도 위반합니다. 프롬프트 개선이나 모델 교체로 없앨 수 있는 성질의 문제가 아니며, 검증 레이어가 유일한 방어선입니다. "LLM 출력을 검증 전까지 신뢰하지 않는다"는 설계 원칙이 실측으로 세 번 뒷받침됩니다.
