## 지연

**순차 실행에서 측정한 지연은 모델 비교에 사용할 수 없습니다.** 실행 순서가 값을 지배합니다.

| 모델 | 단독 실행 | 순차 평가 중 | 실행 순서 |
|---|---:|---:|---:|
| gemma3:4b | 28.7 tok/s | 15.0 | 2번째 |
| qwen2.5:7b | 18.1 tok/s | 4.1 | 4번째 |
| exaone3.5:7.8b | 17.1 tok/s | 4.1 | 5번째 |
| aya-expanse:8b | 15.8 tok/s | 4.1 | 6번째 |
| qwen3:8b | 15.7 tok/s | 9.6 | 1번째 |
| gemma2:9b | 15.6 tok/s | 2.3 | 3번째 |

3번째 모델부터 계단식으로 저하됩니다. Ollama가 모델을 5분간 메모리에 유지하므로 RAM 16GB에서 5GB급 모델이 겹쳐 상주하며 압박이 누적됩니다. 검증: 평가 중 2.3 tok/s였던 `gemma2:9b`를 다른 모델을 모두 언로드한 뒤 단독 실행하니 15.3 tok/s로 복귀했습니다.

단독 측정 기준으로는 **`gemma3:4b`만 뚜렷하게 빠르고(28.7), 나머지 5개는 15~18 tok/s로 동급**입니다.

## 결론

### 1. 2026-08-20 커밋 `9185907`의 qwen3 승격은 정당했다

| | gemma2:9b | qwen3:8b |
|---|---|---|
| 보정 통과 | 4/12 | 7/12 |
| 점수 | 67.5 | 82.5 |

동일 케이스(김치찌개)에서 두 모델 모두 핵심 재료 5개(신김치·돼지고기·두부·대파·고춧가루)를 정확히 뽑았으나, gemma2는 **5개 전부 분량(`amount`)이 비어 있었습니다**. 이것이 `INGREDIENT_AMOUNT_REQUIRED` 반복의 정체이며, 커밋 `9185907`의 "구조 검증을 안정적으로 지키지 못한다"는 판단이 현재 파라미터에서도 재현됩니다.

2026-07-16 평가가 gemma2를 추천한 것은 성능 우위 때문이 아니라 당시 유일하게 실행 가능한 후보였기 때문입니다(원본 리포트: "gemma2:latest is the current recommendation only because it is the only runnable candidate").

### 2. qwen3의 `think=false` 방식을 유지한다

thinking 모드가 없는 `qwen2.5:7b`와 비교해 qwen3가 보정 통과 7/12 대 4/12, 점수 82.5 대 74.6으로 앞섭니다. 커밋 `be415ea`의 해법을 바꿀 근거가 없습니다.

### 3. 한국어 특화 모델이 유리하지 않았다 — 원인은 언어가 아니라 문체

`exaone3.5:7.8b`가 최하위(보정 2/12)이고 실패 11건 중 7건이 `EXCESSIVE_SAFETY_NOTE`입니다. 김치찌개 케이스에서 다른 모델이 재료 5개를 뽑을 때 exaone은 8개(물·다진 마늘·참기름 추가)를 뽑았습니다. 한국어 표현 자체는 6개 모델 중 가장 자연스러웠고 조리 팁까지 덧붙였으나, 그 장황함이 스키마에서 감점 요인이 됐습니다. 프롬프트로 출력 분량을 억제하면 결과가 달라질 여지가 있습니다.

### 4. 모델 선택보다 프롬프트 수정이 효과가 크다

| 코드 | 실패 모델 수 |
|---|---|
| `COOKING_TEMPERATURE_REQUIRED` (에어프라이어 케이스) | 6개 중 5개 |
| `COOKING_HEAT_REQUIRED` + `COOKING_MINUTES_REQUIRED` | 거의 전 모델 |
| `STEP_INGREDIENT_NOT_DECLARED` / `DECLARED_INGREDIENT_NOT_USED` | 전 모델 |

6개 모델이 같은 코드에서 걸린다면 모델 능력이 아니라 **프롬프트가 요구사항을 전달하지 못하는 것**으로 보는 편이 타당합니다.

## 권장

- **기본 모델은 `qwen3:8b` 유지.** 보정 후 최고 성능이며 교체 근거가 없습니다.
- **차선은 `gemma3:4b`.** 보정 통과율이 동일하고 단독 속도가 1.8배입니다. 응답 지연이 제약이 되면 1순위 후보입니다. 다만 표본이 케이스당 1회이므로 동률 확정에는 반복 측정이 필요합니다.
- **우선순위는 모델 교체가 아니라 `RecipePromptFactory` 수정.**

## 측정 방법론 — 반드시 지킬 것

1. **절전 차단 필수.** 1차 실행은 시스템이 74회 sleep/wake하여 통째로 오염됐습니다(`pmset -g log` 기준). 벽시계 측정이 수면 구간을 포함했고 Reactor 타임아웃도 함께 정지해 상한이 동작하지 않았습니다. `caffeinate -dimsu`로 감싸야 합니다.
2. **모델 간 언로드 필수.** 언로드 없이 순차 실행하면 3번째 모델부터 지연이 오염됩니다. 지연을 재려면 모델별로 `ollama stop` 후 단독 측정해야 합니다.
3. **지연과 품질을 분리.** 품질(통과율·점수·검증기 코드·응답 원문)은 순차 실행으로도 유효합니다. 수면이나 메모리 압박은 출력 내용을 바꾸지 않습니다.

`eval.sh`에 1·2번을 반영하는 것을 권장합니다(미적용).

| 항목 | 결과 |
|---|---|
| 모델 단독 실행 | `gemma3:12b`도 10.6 tok/s로 정상 |

## 알레르겐 판정 오탐 — 후속 작업 입력

이번 측정에서 확보한 오탐 사례는 알레르겐 판정 개선 작업의 근거 자료입니다.

```
입력 유형    알레르기 회피를 설명하는 정상 응답
표본         6건 (새우 5, 돼지고기·밀가루·우유 다수 중 개별 검증)
legacy 판정  전부 충돌
실제 누출    0건
```

패턴은 모두 동일합니다. 모델이 회피 사실을 설명하려고 재료명을 언급하고, `AllergenMatcher.findConflicts`가 토큰 부분 문자열 일치로 충돌 처리합니다. 프로덕션은 채팅 응답 본문을 이렇게 스캔하지 않으므로(제목·재료·조리단계만) 현재 사용자에게 직접 영향을 주지는 않습니다. 다만 판정 범위를 넓히면 그대로 재현될 문제입니다.
